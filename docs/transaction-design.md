# 거래 관리 설계 초안

상태: 사용자 선택으로 인증·JWT를 먼저 구현했다. 거래 설계는 검토 대기이며 현재 API와 DB에는 적용하지 않았다. 향후 거래의 회원 ID도 JWT subject에서 가져오고 클라이언트 memberId는 받지 않는다.

## 범위와 동작

- 거래 유형: `INCOME`, `EXPENSE`, `TRANSFER_IN`, `TRANSFER_OUT`.
- 금액은 항상 양수이고 유형이 잔액에 더할지 뺄지를 결정한다.
- 현재 잔액 = 초기 잔액 + 수입 + 이체 입금 - 지출 - 이체 출금.
- 초기 잔액 10,000원에서 수입 2,000원, 지출 3,000원을 등록하면 조회 잔액은 9,000원이다.
- 이체는 같은 회원의 서로 다른 두 계좌 사이에서만 허용한다. 한 요청으로 출금·입금 두 건을 함께 저장하고, 한쪽이 실패하면 모두 롤백한다.
- 첫 단계에서는 KRW만 지원하고 잔액 부족 거래를 거절하는 안을 제안한다. 기존 계좌의 통화와 잔액 정책은 구현 전에 확인한다.

## 데이터와 계층

`transaction` 기능 패키지 아래 controller/service/repository/domain/dto를 둔다. 테이블명은 마스터 문서에 맞춰 `financial_transactions`로 제안한다.

거래 필드 후보: id, account_id, category_id, type, amount(NUMERIC(19,2)), occurred_at, memo, transfer_id, created_at. 계좌·발생 시각·ID 조회용 인덱스를 둔다. 인증에서 V2를 사용했으므로 거래 구현 시 다음 migration 버전으로 추가한다. 기존 V1/V2는 수정하지 않는다.

일반 거래 등록 API는 수입·지출만 받는다. 이체 유형은 이체 서비스가 생성해 한쪽 거래만 저장되는 상황을 막는다. 이체 수정은 두 거래를 함께 수정해야 한다. 첫 구현은 수입·지출 등록/수정과 이체 등록으로 나누고, 이체 수정은 별도 설계 후 제공하는 안을 제안한다.

잔액은 거래 합산으로 조회하고 초기 잔액을 덮어쓰지 않는다. 잔액 부족 검사와 거래 쓰기 사이의 경쟁을 막으려면 관련 계좌를 잠근다. 이체에서는 계좌 ID 오름차순으로 잠가 교착 가능성을 줄인다. 같은 계좌에 쓰는 모든 경로에서 같은 잠금 규칙을 적용한다.

## API 후보

| Method | 경로 | 목적 |
|---|---|---|
| POST | `/api/v1/accounts/{id}/transactions` | 수입·지출 등록 |
| GET | `/api/v1/accounts/{id}/transactions` | 페이지 단위 목록 |
| PATCH | `/api/v1/accounts/{id}/transactions/{transactionId}` | 수입·지출 수정 |
| POST | `/api/v1/transfers` | 두 계좌 간 이체 |

금액은 Java에서 BigDecimal로 계산하고 DB 저장 전에 소수 자릿수·최대 정밀도를 검증한다. JSON number 계약을 유지한다면 FE에서 안전하게 표현할 수 있는 금액 범위도 제한해야 한다. 계약 변경 시 Java DTO, FE 타입, `api-contract.md`를 함께 변경한다.

## 검증과 학습 포인트

- 수입·지출·수정 전후 잔액, 초기 잔액 0, 소수 금액을 검증한다.
- 0/음수/정밀도 초과, 없는 계좌, 다른 회원 계좌, 잔액 부족, 같은 계좌 이체, 통화 불일치를 거절한다.
- 이체 중 실패 시 양쪽 저장 취소, 동시 출금 시 잔액 부족 방지, 중복 요청 처리 정책을 PostgreSQL 통합 테스트로 검증한다.
- BigDecimal은 문자열로 생성하고 `compareTo`로 금액 크기를 비교한다.
- `@Transactional`은 이체 두 건을 하나의 작업으로 묶지만, 그 자체만으로 동시 출금 경쟁을 막지는 않는다.

다음 구현 전에 잔액 부족 허용 여부, KRW 제한, 이체 수정 범위 및 중복 요청 정책을 사용자와 확정한다.
